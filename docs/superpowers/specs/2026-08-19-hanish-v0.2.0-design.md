# Hanish v0.2.0 Trust and Host 0 Design

Date: 2026-08-19  
Status: approved design, pending implementation  
Base: `v0.1.2` / `24e1281`

## Purpose

Hanish v0.2.0 makes the existing forecasting substrate trustworthy enough to
host a real GitHub Actions stream. It corrects false provenance, makes
exposure exclusions append-only and effective, proves replay determinism,
bounds hot-path work, gives CI a stable distributed identity model, exports
verifiable experiment receipts, and adds Host Omega adversarial conformance.

This release does not begin the Moneta + Octavius + Hanish temporal ablation,
model-authored forecasting, calibration buckets, or intervention policy.

## Invariants

Every change must preserve the eight laws:

1. host-facing capture and processing never raise;
2. incomplete or invalid evidence never becomes a MISS;
3. history is append-only and corrections are new records;
4. the core remains domain-blind;
5. the resolution rule and forecast exist before eligible evidence;
6. the runtime core has zero dependencies;
7. the first valid terminal observation is final;
8. exposed forecasts never contribute to calibration.

The dependency lattice remains:

`time <- past <- future <- present <- adapters`

Operational caches and indexes are always derived and rebuildable. They are
never epistemic authority.

## Release shape

The work lands as one `v0.2.0` release because it introduces schema-v2 records
and tightens authoring contracts. It is implemented in ordered internal
commits, then published in two phases:

1. Push the code and workflow. GitHub Actions produces a candidate Host 0
   receipt artifact.
2. Download and verify that artifact, commit it add-only under
   `experiments/receipts/`, rerun CI, merge or fast-forward according to the
   repository's established convention, and publish `v0.2.0`.

CI never pushes to the repository. An Actions artifact is transport with
finite retention; it becomes authoritative only after promotion into git.

## 2. Schema v2 and structural exposure

### Forecast immutability

Make `Forecast` immutable. `Substrate.author()` stores and registers a
detached canonical value, so a caller cannot mutate exposure or any other
field after the record is appended.

### Exposure basis

Add an immutable, domain-blind `ExposureBasis` containing:

- `author_ref`;
- identities that saw the forecast before resolution;
- identities capable of moving the target observable;
- completeness flags for both identity sets;
- a non-empty separation-control or embargo reference;
- an attesting host identity and attestation timestamp.

Exposure is derived conservatively:

- any intersection between author/audience and capable actors is `EXPOSED`;
- missing lists, false completeness flags, absent controls, or unproved
  separation default to `EXPOSED`;
- `BLIND` authoring requires both sets to be explicitly complete, disjoint,
  covered by a named separation control, and attested by the host;
- an explicitly `EXPOSED` forecast may omit a basis.

Legacy v1 forecasts remain readable. New schema-v2 authoring cannot write a
caller-labelled `BLIND` forecast without a valid basis.

### Monotone amendments

Add an immutable `ExposureAmendment` record to `forecasts.jsonl`. It carries
the forecast ID, target canonical digest, reason code, author, timestamp, and
the only permitted transition: `BLIND -> EXPOSED`.

Amendments are idempotent and can only remove calibration eligibility. They
cannot alter probability, resolution, verdict, observation identity, Brier
score, or any other historical fact. Replay folds forecasts first and
amendments second. The raw outcome record remains unchanged; the canonical
derived `Outcome` is an immutable replacement with
`calibration_eligible=false`.

The schema-v2 kind/version dispatch is explicit:

- unkinded v1 forecast/outcome records retain their legacy interpretation;
- v2 forecast and amendment records carry `_kind`;
- unsupported future versions fail loudly;
- zero, negative, boolean, and non-integer versions are corruption;
- a v1 reader must fail loudly on a v2 record rather than ignore an
  amendment and count excluded calibration.

## 3. Replay determinism gate

Add a subprocess replay probe and a pytest gate that runs identical fixed
ledger fixtures under at least two distinct `PYTHONHASHSEED` values. Land it
in two explicit steps so it can protect the schema migration it later covers:

1. a v1-only fixed fixture and pinned digest land before any core change;
2. after schema v2 exists, extend the fixture with v2 forecasts and amendments
   and intentionally update the pinned digest in the same reviewed commit.

The final fixture uses fixed IDs and timestamps and contains mixed v1/v2
records, valid and invalid evidence, seals, provisional and settled outcomes,
and an exposure amendment. Each subprocess must prove its salted string hash
differs, rebuild the same semantic state, emit canonical JSON, and match a
pinned SHA-256 digest. Paths, mtimes, lock files, and operational copy
artifacts are excluded; semantically ordered evidence remains ordered.

This gate lands before the remaining core changes and runs in every supported
Python CI leg.

## 4. Evidence capture watermark

Replace the full-ledger scan in `append_observation_once()` with an atomic
byte-offset tail synchronization performed under the existing evidence lock.

At construction, obtain a complete-line evidence snapshot and exact EOF
watermark. On capture:

1. acquire the evidence lock;
2. validate the watermark and repair a post-open torn tail;
3. read and decode only complete records since the watermark;
4. return every newly discovered observation and seal to the caller;
5. detect the requested dedup identity;
6. append and fsync only if no durable winner exists;
7. return the new watermark and actual durable winner.

The substrate merges all returned tail records into derived state before
advancing its watermark. A race loser ingests the durable winner immediately,
so it can resolve without restart. Same identity plus a different canonical
payload is an `identity_conflict`, not an ordinary duplicate.

If the watermark is past EOF, not on a record boundary, or the prefix identity
changed, safely fall back to a full locked rescan. Initial reopen remains
O(N); subsequent captures are O(records appended since the last synchronized
snapshot), not O(total history).

## 5. Incremental resolution and terminal concurrency

Build derived indexes:

- `observations_by_key[(subject_ref, observable)]` in ledger order;
- `cursor_by_forecast[forecast_id]` within that key-local list;
- a deterministic dirty queue of unresolved or provisionally
  `UNRESOLVABLE` forecasts;
- sequence membership by `(source_ref, epoch_ref)` for completeness.

New evidence dirties only existing watchers for its key. A newly registered
forecast starts at cursor zero and receives one key-local historical backfill.
This preserves late registration/replay when the forecast's `created_at`
precedes the observation's `arrived_at`, while evidence that predates the
forecast is ineligible and cannot enable hindsight scoring. Malformed or
ambiguous timestamps fail closed.

Each dirty forecast advances past invalid, unacceptable, or post-horizon
observations once and stops permanently at its first valid terminal. Repeated
`process()` calls with no changes perform no evidence comparisons. On reopen,
all indexes and cursors are rebuilt; unresolved and provisional forecasts are
dirtied, while settled forecasts remain final.

Outcome emission becomes compare-and-append under the outcome ledger lock:

- the first settled terminal outcome wins;
- `UNRESOLVABLE` is provisional and may be followed by one settled outcome;
- later settled outcomes are rejected and counted;
- replay uses the same monotone fold instead of last-record-wins.

## 6. Honest world references

The legacy CI digest is immediately classified `IDENTIFIABLE`, not
`REPLAYABLE`.

Define `WorldManifest` as two immutable records with different epistemic
times:

- a pre-evidence `WorldCommitment`, authored with the forecast, covering the
  repository and tested commit, exact workflow bytes or immutable blob
  coordinate plus digest, Host 0 plan bytes and digest, adapter/ledger schema,
  dependency constraints or lock, and intended commands/environment;
- a post-run `ExecutionInventory`, stored in the receipt, covering actual
  resolved dependencies, action commit SHAs, interpreter, runner image, and
  commands executed.

The commitment uses canonical JSON and a full SHA-256 reference:
`world:sha256:<64 hex>`. The later inventory is evidence about the execution;
it never rewrites the earlier world reference.

A commitment is `REPLAYABLE` only when every required input, including the
environment and dependency resolution, is fully pinned and known before
evidence exists, and each artifact has embedded bytes or an immutable
retrievable locator plus SHA-256 and size. Missing artifacts, ranged
dependencies, mutable tags/runner images, truncated digests, or unverifiable
locators make it `IDENTIFIABLE`. The first Host 0 run is expected to be
`IDENTIFIABLE`; its execution inventory may enable a later fully pinned run
but cannot retroactively promote this one. New manifest-less `REPLAYABLE`
forecasts are rejected; legacy 16-hex references load honestly as
identifiable.

CI-specific construction and replay remain in the adapter layer. The core
stores an opaque canonical commitment and validates only the generic presence,
capability, and digest contract.

## 7. Host 0 CI vertical slice

### Independent plan authority

Commit `.github/host0-plan.json` with the expected legs and deterministic
slots. The first plan contains:

- Python 3.11, 3.12, 3.13, and 3.14 test legs in slots 1-4;
- one package-build leg in slot 5;
- one commit-level aggregate in slot 6.

The denominator comes from this pre-existing plan, never from the artifacts
that happen to arrive.

### Identity

- subject: `git:<tested-checkout-sha>`;
- epoch: repository + workflow ref + run ID + run attempt;
- source: repository-scoped `github-actions:<owner>/<repository>` (GitHub run
  IDs are only repository-scoped, so a global source would permit collisions);
- leg: canonical plan ID, not a display name;
- sequence: deterministic plan slot, independent of process lifetime and
  arrival order.

`CompletenessSeal` gains a subject reference so commit identity and run-attempt
epoch are no longer conflated. V1 seals migrate with
`subject_ref=epoch_ref`.

### Aggregation

The adapter owns immutable run identity, leg report, plan, and aggregate
types. A standard-library CLI exposes commands to author the operational
forecast, write a leg report, aggregate/capture/finalize, export a receipt,
and verify a receipt.

The aggregator validates exact leg membership and common run coordinates. It
uses the declared boolean observable `ci.required_leg_pass` for slots 1-5.
Each event identity is
`run-<run_id>:attempt-<attempt>:leg-<canonical_leg_id>` and its metadata carries
the plan digest, slot, tested SHA, workflow ref, and leg ID. No leg event may
emit the commit-level observable. The slot-6 event identity is
`run-<run_id>:attempt-<attempt>:aggregate-required-checks` and alone emits
`ci.required_checks_pass`.

The aggregator captures one observation per valid expected leg and exactly
one commit-level observation when every required leg is accounted for. A
genuine test or build failure is valid `False` evidence. A missing, duplicate,
malformed, wrong-SHA, wrong-attempt, cancelled, or infrastructure-failed
report produces no valid aggregate and a non-complete seal, preserving
`UNRESOLVABLE`. Both observables are declared by `CIAdapter` with strict bool
value types and the adapter's configured source.

Completeness requires exactly one record for every slot `1..N`, no duplicate
sequence values, a matching subject and epoch, and a first-write/effect-once
seal. Negative, boolean, non-integer, or unreasonably large sequence/final
values cannot certify completeness. Conflicting refinalization is rejected and
counted.

### Workflow

The workflow uses read-only repository permissions and never self-pushes.

1. A forecast job creates an `EXPOSED`, non-calibration operational forecast
   and world commitment before test evidence exists. Failure is fail-open to
   the test/build jobs.
2. Four matrix jobs run lint/test/demo and always attempt uniquely named leg
   reports without changing their real test conclusion.
3. A dedicated package job installs `build` and runs `python -m build` as G9.
4. An `if: always()` Host 0 job downloads the forecast and leg artifacts,
   aggregates through `CIAdapter`, captures/finalizes an ephemeral substrate,
   and uploads a candidate receipt. Host 0 failure cannot make otherwise-green
   product checks fail.

The first receipt proves autonomous evidence capture, aggregation,
completeness, and replay. It does not claim calibration or a model-authored
forecast.

## 8. Experiment receipts

Live roots remain ignored. A promoted receipt is a new immutable directory:

`experiments/receipts/<run-id>-<attempt>-<digest>/`

It contains the operational forecast, exposure basis/amendments, world
commitment, execution inventory, committed Host 0 plan, canonical leg reports,
evidence ledger, completeness seal, outcome ledger, observable declarations,
code/workflow SHAs, and reproduction command.

`manifest.json` is non-circular: it lists the relative path, byte size, and
SHA-256 of every payload file except itself. `manifest_root` is the SHA-256 of
the canonical sorted entry list. The directory name ends in the first 16 hex
characters of that root; the complete root remains in the manifest.

`verify-receipt` checks exact payload membership, size, SHA-256, manifest-root
and directory-name agreement, world-commitment/inventory integrity, semantic
replay, expected subject/epoch/plan, effective calibration eligibility, and
the pinned semantic state digest. CI verifies every committed receipt and
applies `experiments/calibration-exclusions.jsonl` before exposing calibration
samples.

An add-only workflow check compares research artifacts with an authoritative
git base. Pull requests use the PR base SHA. Pushes use the event's pre-push
SHA (`github.event.before`), covering the complete pushed range rather than
only `HEAD^`; branch-creation zero SHAs fall back to the merge base with the
default branch. Any modified, renamed, or deleted path under
`experiments/receipts/` fails. Only new receipt directories/files are allowed.

The same check protects `experiments/calibration-exclusions.jsonl` with a
prefix rule: the exact bytes at the authoritative base must be an unchanged
prefix of the new file, and every added suffix must contain complete,
schema-valid newline-delimited records. Editing, truncating, reordering, or
deleting an exclusion fails. Git history is the long-term immutability
authority. Corrections create a new amendment/receipt or append an exclusion;
an existing receipt or exclusion record is never edited in place.

## 9. Host Omega conformance

Add a reusable hostile-host fixture and adapter-contract suite. It covers:

- never-raise faults in values, timestamps, I/O, locks, and decoding;
- strict value types, including bool versus int;
- duplicates, identity conflicts, two processes, cold reopen, and tail sync;
- out-of-order arrival, invalid-first, retry laundering, and late registration;
- provisional versus settled outcomes and concurrent terminal races;
- gaps, duplicate/invalid sequences, seal-before-events, repeated/conflicting
  seals, foreign sources/subjects, and adapter restart mid-epoch;
- exposure derivation, monotone amendment, and caller-object immutability;
- manifest loss/corruption and legacy downgrade;
- mixed schema versions, unknown kinds, torn tails, and interior corruption;
- namespace collisions between two hosts.

The suite runs against Host Omega and `CIAdapter`. A production Host 0 workflow
is not considered complete until the local contract suite and one live Actions
candidate receipt both pass.

## Stop conditions

Stop rather than weaken a law if any of the following occurs:

- the authentic historical runtime ledger remains unavailable: retain the
  correction, do not create a fake receipt;
- an Actions artifact is missing or malformed: keep the run unpromoted and
  `UNRESOLVABLE`;
- the candidate receipt cannot replay identically: do not release;
- CI integration can break an otherwise valid host build: restore fail-open
  behavior before landing;
- a proposed optimization changes first-valid-terminal ordering: reject the
  optimization;
- completing the work would require beginning temporal ablation or
  model-authored calibration: defer it to the later milestone.
